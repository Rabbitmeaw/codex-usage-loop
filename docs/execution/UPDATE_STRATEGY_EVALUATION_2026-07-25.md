# 更新策略评估

日期：2026-07-25

## 结论

当前不应增加自动更新，也不建议增加由 CodexUsageLoop 自身联网的“检查更新”。

推荐只增加一个用户主动入口：

> 在浏览器查看 GitHub Releases…

该入口只在用户点击后调用 macOS 打开硬编码的官方 Releases URL。CodexUsageLoop 自身不发送 HTTP 请求、不判断版本、不下载、不安装、不定时检查，也不保存更新检查状态。

这不是“自动更新”的折中实现，而是一个明确的外部文档／下载入口。

## 核心理由

### 1. 保留清晰的隐私边界

项目当前最重要的信任陈述不是抽象的“完全离线”，而是：

- CodexUsageLoop 自身不主动访问互联网。
- 仅通过本机 `codex app-server --stdio` 读取用量。
- 不上传用量、窗口信息或屏幕画面。
- 屏幕截图只在本机内存中用于定位，随后丢弃。

如果加入 `URLSession`、GitHub API 或更新框架，即使只在用户点击后请求版本，也会把隐私声明变成带条件的解释，并增加用户对“屏幕录制权限是否会与联网能力组合使用”的合理疑虑。

仅打开默认浏览器可保持边界简单：网络访问由用户明确触发并发生在浏览器中，而不是发生在拥有屏幕录制权限的 CodexUsageLoop 进程中。

### 2. 当前发布安全条件不适合自动安装

项目 Release 当前没有 Developer ID 签名或 Apple 公证。SHA-256 能验证下载完整性，但不能独立证明发布者身份；仓库账号或 Release 供应链被攻破时，同一发布页提供的校验和也可能一起被替换。

自动下载和安装会把风险从“用户查看并决定”提前到应用执行路径中。当前发布模型不具备引入自动安装所需的签名更新清单、可信工件验证、失败回滚和公证链路。

### 3. 应用内版本检查的收益不足以覆盖复杂度

用户主动点击后由应用联网检查版本，仍需要处理：

- GitHub API 或版本 feed 的离线、超时与限流。
- SemVer、预发布版本和版本比较。
- 请求元数据、User-Agent 与潜在指纹。
- 网络错误、状态展示和测试。
- 新的隐私声明与威胁评审。

这些复杂度只节省了用户在 Releases 页面查看当前版本的一步，当前没有足够收益。

## 方案比较

| 方案 | 隐私边界 | 更新可发现性 | 实现与安全成本 | 结论 |
| --- | --- | --- | --- | --- |
| 完全不提供入口 | 最小 | 低 | 最低 | 可接受，但用户容易错过兼容性修复 |
| 用户点击后在浏览器打开 Releases | 应用自身仍不联网 | 中 | 很低 | 推荐 |
| 用户点击后由应用联网检查版本 | 引入条件式联网 | 高 | 中 | 当前不推荐 |
| 后台检查或自动更新 | 明显改变产品边界 | 高 | 很高 | 明确不采用 |

## 推荐实现边界

如果后续决定增加入口，保持为最小实现：

- 菜单项：`在浏览器查看 GitHub Releases…`
- URL：硬编码 `https://github.com/Rabbitmeaw/codex-usage-loop/releases`
- 行为：仅使用 `NSWorkspace` 打开默认浏览器。
- 不引入 `URLSession`、Sparkle 或其他更新依赖。
- 不在启动、定时器或后台发起请求。
- 不下载或执行任何文件。
- 不保存点击、版本或检查状态。
- 不从远端返回内容中读取或跳转 URL。
- 如显示当前版本，从 Bundle 元数据读取，避免增加新的硬编码版本源。

不建议使用“检查更新”作为菜单文案，因为该名称通常暗示应用会联网比较版本。

## 推荐用户文案

菜单提示：

> 仅在点击后打开默认浏览器；本应用不会检查、下载或安装更新。

隐私说明：

> CodexUsageLoop 不会主动访问互联网。只有当你选择“在浏览器查看 GitHub Releases…”时，macOS 才会在默认浏览器打开官方发布页；GitHub 会按其隐私政策处理浏览器连接。用量、窗口信息和屏幕画面不会由 CodexUsageLoop 发送。

这里应使用“应用自身不主动联网”，避免把本机 `codex app-server` 或用户浏览器的行为混同为整个系统绝对离线。

## 未来重新评估条件

只有同时出现以下条件时，才值得重新评估“用户主动点击后由应用检查版本”：

1. 用户明确反馈需要应用内判断“有／无更新”。
2. 发布频率或 Codex 兼容性变化使浏览器入口明显不足。
3. 存在稳定、最小、可审计的版本 feed。
4. 项目愿意公开接受“仅用户点击时联网”的新隐私边界。

自动更新不应进入当前路线图。若未来产品定位发生变化，至少先完成 Developer ID 签名与公证、独立签名的更新清单、工件验证、明确 opt-in、失败回滚，以及新的隐私 ADR 与威胁评审。

## 建议决策

建议后续在用户确认后记录一项 ADR：

- 不自动更新。
- 不在启动或后台检查更新。
- CodexUsageLoop 自身不请求版本信息。
- 只提供用户显式打开官方 GitHub Releases 的浏览器入口。

评估阶段未修改应用菜单或网络行为；后续实施状态见下节。

## 实施状态

用户已确认采用推荐方案。B34 在 macOS 增加“在浏览器查看 GitHub Releases…”菜单项，只调用 `NSWorkspace` 打开硬编码官方 URL；B36 在 Windows 增加相同入口，仅通过 `ProcessStartInfo.UseShellExecute` 交给默认浏览器。两个平台都未引入应用内版本请求、下载、安装、后台检查或更新状态持久化。
