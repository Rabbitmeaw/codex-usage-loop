# CodexUsageLoop v0.1.5

v0.1.5 修复一类与网络环境相关的用量中断：系统代理已配置、但本机到 Codex 服务的直连暂时不可用时，圆环与用量卡片拿不到数据或停留在旧值。

## 主要变化

### 修复用量刷新在网络波动时中断（macOS）

- 用量数据由本机 `codex app-server --stdio` 子进程提供；该进程只识别 `HTTP_PROXY`／`HTTPS_PROXY`／`ALL_PROXY` 环境变量，不读取 macOS 系统代理设置。此前从菜单栏启动时子进程不带这些变量，只能直连：直连可用时一切正常，直连不可用时请求静默超时，用量即中断且表现为时好时坏。
- 现在启动 app-server 时，应用会读取当前 macOS 系统代理设置（支持手动 HTTP、HTTPS 与 SOCKS，任意主机和端口），把已启用的代理注入为子进程环境变量；应用自身环境里已有代理变量时不覆盖。应用自身仍然不发起任何网络请求，app-server 的网络行为与在终端中运行一致。
- 明确边界：PAC 自动代理配置与需要用户名密码认证的代理不在本次支持范围；未配置系统代理时行为与之前相同。

### 其他平台

- Windows 无改动：Windows 上的 app-server 自行读取系统注册表代理，不受此问题影响。

## 验证

- 实证闭环：同一机器上，无代理环境变量时 `account/rateLimits/read` 在 codex-cli `0.153.4` 与内置 `0.159.2` 上均无响应；注入系统代理变量后立即返回正确额度（7 天窗口 33%，credits 余额 62500）。
- macOS：90 项 Swift 测试、Release 构建和严格签名校验通过；本机已验证修复版启动的 app-server 带代理环境变量且用量正常显示。
- 本次回归环境：macOS `26.7.1`，ChatGPT Desktop `26.928.21956`（build `12404`，内置 codex-cli `0.159.2`）与 Codex CLI `0.153.4`（npm/nvm）。本 Release 仅承诺这组已记录环境和本仓库的能力契约，不假定后续版本兼容。

## 本地处理与权限边界

CodexUsageLoop 不读取认证文件，不保存或上传截图，也不发起自有 HTTP 请求。用量仅经本机 `codex app-server --stdio` 读取；本次修复只是把用户在系统设置中已配置的代理地址以环境变量形式传给该子进程，不新增网络边界。Codex CLI／app-server 自身的网络行为，以及用户明确打开 Releases 后的默认浏览器连接，属于各自独立边界。

macOS 14+ 的像素级定位仅在用户从菜单主动请求并自行授予屏幕录制权限后启用；定位图像只在 CodexUsageLoop 进程内存中分析。屏幕录制仍是可访问屏幕内容的敏感系统权限，这些实现边界不是“绝对安全”或“零风险”承诺。
